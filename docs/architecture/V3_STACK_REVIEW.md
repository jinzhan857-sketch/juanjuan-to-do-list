日期：2026年11月16日。源码基准：main e5b1776。状态：静态评审与推荐草案，待展确认新增选型并经原任务验证；不是已经采用或实施的架构。

## 推荐结论与确认状态

建议采用React与Next.js组织前端，Node.js与Fastify组织一个按职责分模块的业务后端，延续PostgreSQL及Supabase账户方向。新工程建议逐模块采用TypeScript，现有可复用JavaScript不先整体翻译。实际依赖及版本须在原任务确认、锁定和验证。

| 层次 | 推荐 | 目前属于什么决定 |
| --- | --- | --- |
| 页面工程 | React组件与Next.js App Router | Next.js方向及只读待办首试点已由[0005](../decisions/0005-incremental-nextjs-migration.md)确认；具体版本、渲染和托管仍待#123核对 |
| 语言 | 新前后端模块优先TypeScript，复用现有JavaScript | 新建议，尚未取代[0002](../decisions/0002-backend-language.md)中“未决定TypeScript”的状态 |

| 业务API | Node.js加Fastify，一个模块化业务服务 | 新建议，需#11确认取舍，#12验证宿主，#14验证最小真实链路 |

| 设备数据 | 保留IndexedDB及明确的本地未同步记录 | 本地连续性方向保留；不是把全局S搬入React或后端 |
| 数据访问 | 先以pg驱动与显式SQL事务验证；暂不冻结ORM | 新建议；实际客户端、连接池与迁移工具在#12、#14验证后确定 |

| AI及配置 | 复用现有模型适配、候选确认与受控执行边界，逐步服务端化 | #16、#17主维护；本次不预选另一套Agent编排平台 |

这些工具分工不同。React和Vue属于同层选择；Next.js基于React，Nuxt基于Vue。Node.js是运行环境，Fastify、NestJS和Express才是业务后端框架。Supabase提供数据库、账户等服务，不能替代卷卷自己的业务规则。

## 前端比较：React还是Vue

| 组合 | 对卷卷的价值 | 需要承担的成本 | 本轮判断 |
| --- | --- | --- | --- |
| React与Next.js | 组件、页面路由与构建有统一工程入口；可先保留浏览器数据，再按需求使用服务端能力 | 必须理解组件状态、客户端与服务端边界，避免重复缓存或错误地在服务器读本地库 | 首选，延续已确认的#123路线 |
| Vue与Nuxt | Vue模板接近HTML表达，Nuxt提供页面约定及构建；同样能做卷卷的交互应用 | 要重新确认0005和#123，并重做相应技术试点；不能同时维护React和Vue两套页面工程 | 合理备选，当前没有足以改变既定方向的明确收益 |
| React与Vite | 适合保持纯浏览器应用，构建与页面组件分工直接 | 路由、数据加载等工程组合需要另选；未来服务端与部署仍须设计 | 若长期只做本地前端可再考虑，本轮不另开迁移路线 |
| 保持原生单页 | 可以复用现有实现，眼前迁移成本最低 | 页面、状态和业务集中问题仍需自行解决 | 不作为3.0长期页面工程目标 |

当前仍是原生工程，并没有大量现存React组件，因此Vue在技术上完全可行。推荐React与Next.js是结合已确认方向和减少重复试点的项目判断，不是认定Vue能力不足，也不是以流行度或招聘印象代替评审。

React官方将Next.js列为框架选择之一；Nuxt官方说明其基于Vue。Vite是构建工具，不是React或Vue的替代品。依据：[React建应用](https://react.dev/learn/creating-a-react-app)、[Vue介绍](https://vuejs.org/guide/introduction.html)、[Nuxt介绍](https://nuxt.com/docs/4.x/getting-started/introduction)、[Vite介绍](https://vite.dev/guide/)。

## 后端比较：Fastify、NestJS还是Next.js自身接口

| 候选 | 适合之处 | 对卷卷的代价或限制 | 本轮判断 |
| --- | --- | --- | --- |
| Fastify | 有请求校验、模块封装及不启动网络端口的API测试方式，便于逐条接入现有规则 | 仍须自己定义业务模块、错误、鉴权和事务边界；插件注册及作用域不能随意堆叠 | 推荐作为#14首个验证候选 |
| NestJS | 控制器、服务、模块及依赖注入形成较统一的组织约定 | 需要掌握更多框架生命周期和配置；对当前小团队，投入是否换来实际维护收益尚未证明 | 若未来团队和模块明显扩大，可复评；本次不作为默认选择 |
| Express | 接口组织灵活、基础层直接 | 校验、模块边界和错误处理需要另行统一，容易由不同实施者各配一套 | 可行备选，当前优先验证Fastify的现成接口约束 |
| 仅用Next.js Route Handlers | 网页和接口可以放在同一工程，减少独立API服务的发布工作 | 业务可能重新堆进页面工程；调度、任务恢复及宿主限制仍要单独解决 | 可行的简化备选，但需对原“独立后端”决定提出明确变更，不能默默替代 |

Fastify的Schema校验、封装与注入测试是官方能力；适不适合卷卷及维护成本排序是本轮推断，未做性能对测。[校验](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)、[封装](https://fastify.dev/docs/latest/Reference/Encapsulation/)、[测试](https://fastify.dev/docs/latest/Guides/Testing/)。NestJS和Express的比较依据分别是[官方文档](https://docs.nestjs.com/)与[官方介绍](https://expressjs.com/)。NestJS也可使用Fastify适配器，两者并非不能组合；本次没有同时引入两层框架的必要证据。

Next.js能提供接口层，官方也明确其后端能力并非完整后端的替代。采用独立服务是卷卷当前职责与运行需求的推荐，不是说Next.js无法编写业务。[Next.js后端说明](https://nextjs.org/docs/app/guides/backend-for-frontend)。

## 怎样分工，避免把黑盒搬进新框架

推荐一个业务API服务，内部按职责分模块，不先拆微服务或搭建插件平台。网页和API是两个可分别发布的单元，需要维护接口、认证、配置、日志与部署，这是独立后端的实际成本。若#12证明该成本不值得或宿主不适合，应带证据回#11调整，不能靠临时兼容包装维持表面一致。

| 位置 | 主要职责 | 明确边界 |
| --- | --- | --- |
| React组件与页面状态 | 呈现、输入、菜单、候选预览、错误和加载反馈 | 不自行拼跨表事务、不重复计算积分，不持有服务端密钥 |
| 共享规则与合同 | 环境无关的日期、字段、动作类型及可复用纯规则 | 不读DOM、浏览器库或网络；客户端预览与服务端最终核对调用同一来源 |
| Fastify接口层 | HTTP结构检查、认证入口、错误映射、请求标识 | 不把完整业务算法塞进路由或请求钩子 |
| 业务服务 | 真实目标、范围、版本、必要确认、积分与撤销的确定性规则 | 模型、网页及Skill不能绕过它写业务数据 |
| 数据访问层 | 明确账户范围的读取与事务提交、持久动作和操作记录 | 不依赖页面；接口返回成功前必须能够核对真实提交结果 |
| AI与外部工具适配 | 模型、搜索、图片、取消与费用记录 | 外部资料是输入证据，不是用户授权；与业务执行分开 |
| 调度入口 | 按#19确定的持久任务、重试与恢复 | 复用同一业务服务，不靠浏览器开着或内存定时器保证交付 |

共享规则只有一份实现，不代表只校验一次。TypeScript只能提供开发阶段约束，HTTP、模型输出与数据库输入仍要运行时校验；用户可配置内容不能成为可执行Schema。Fastify官方将Schema视作应用代码，也要求数据库等异步核对放在初始结构验证之后。[TypeScript说明](https://www.typescriptlang.org/docs/handbook/intro.html)、[Fastify校验边界](https://fastify.dev/docs/latest/Reference/Validation-and-Serialization/)。

前端优先使用组件本地状态与明确的共享入口，不先把全局S原样搬成一个巨大store。网络查询缓存、本地持久资料、待提交修改与页面状态分别有归属；缓存库不承担同步和冲突解决。出现实际需求后再评估状态或查询库，不同时默认加入多套全局状态管理。

样式先采用共用变量与CSS Modules，必要组件统一复用。Tailwind或整套UI库可以后评估，但不能为了框架完整而预装；设计skill辅助方案及复查，不决定业务边界。[Next.js样式支持](https://nextjs.org/docs/app/getting-started/css)。

## 数据、账户、附件与同步

延续已确认的Supabase与邮箱账户方向，PostgreSQL保存云端业务与动作记录，IndexedDB保留访客数据、缓存及未同步修改。Supabase Auth处理账户和会话，卷卷后端仍核对每次业务访问的身份、归属与动作范围。登录、访客并入、账户切换、冲突与删除规则分别由#13、#15确认，不凭框架默认值冻结。

建议先用pg及明确SQL验证一条完整事务。记录、操作历史和积分等需要同一次数据库事务完成时，不能把数个独立REST写请求当整体提交。pg要求事务内使用同一个客户端连接；是否采用ORM不影响这一业务要求。[pg事务说明](https://node-postgres.com/features/transactions)。

账户隔离不能只靠前端隐藏或以为“用了Supabase就自动安全”。数据库角色、连接方式和实际RLS策略要匹配；管理凭据或具备绕过权限的连接不能被假定受普通用户RLS保护。前端不持有这些凭据，后端也须验证归属和越权目标。[Supabase数据库](https://supabase.com/docs/guides/database/overview)、[Auth](https://supabase.com/docs/guides/auth)、[RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)。

云端图片和附件优先评估Supabase Storage，并独立保存元数据及关联；访问授权、上传中断、删除、孤立对象清理和备份恢复须纳入验收。数据库事务不会自动把外部文件上传也变成同一事务，失败清理与状态必须明确。[Storage说明](https://supabase.com/docs/guides/storage)。

同步首版沿用手动触发、状态可见与冲突可解释的原方向；不因为React、Next.js、Supabase Realtime或缓存工具存在，就声称离线队列、删除传播和双设备冲突已经解决。旧库与真实资料迁移继续单独授权和合成演练。

## 托管、费用和AI运行范围

先由#12比较能运行所选Node.js后端的宿主，再决定静态导出还是需要Node宿主的Next.js功能。静态托管不能执行动态业务API；跨来源、凭证、数据库连接池、调用时限、图片大小、日志和回退都要实测。不预选付费套餐，不承诺国内与香港访问稳定或免费资源永不暂停。

Fastify支持的部署方式不等于某个Serverless宿主适合卷卷的任务时长。用户确认必须持久保存后结束请求，确认发生在数分钟后也能恢复，不保持一个HTTP请求等人点按钮。需要任务调度时按#19验证运行入口，不把它混成更换HTTP框架即可解决的问题。[Next.js静态导出](https://nextjs.org/docs/app/guides/static-exports)、[Fastify部署考虑](https://fastify.dev/docs/latest/Guides/Serverless/)。

Redis继续只按实际额度、限流及已证明的并发需求评估，不作为全部业务事实的第二份数据库。AI请求先复用已有适配和受控流程；不预先引入通用Agent框架、工作流平台或向量数据库。#127知识库、#128产品内Skills仍为候选，先由#11判断场景与范围，不能因本次全栈选型自动升级成3.0硬交付或发布前置。设计开发用skill与产品运行时Skill分别记录。

当前#128候选正文仍写“手选角色的职责边界继续有效”和角色匹配，而已交付#133明确模式仅作意图提示。这是具体的待校正冲突：若采用产品内Skills，由#11、#16、#17在候选设计中对齐统一卷卷入口，权限绑定账户、工具、目标与确认，不能恢复按聊天模式限制能力。此处不把#128候选当成已生效规则，也不顺带实施它。

## 选型通过条件及停止条件

这些是本次选型建议的核对项，具体产品阈值由原任务确认，不新增一套重复活动任务。当前全部未执行。

- [ ] 锁定受支持且互相兼容的运行环境与依赖；新工程干净安装、构建和静态或服务端入口可复现。
- [ ] 只读待办试点证明组件、数据和展示状态分工清楚；筛选、计数、详情及重开不写业务资料。
- [ ] 接口测试能直接加载实际服务与模块，不再为纯业务验证提取整页脚本。保留原正确规则与失败对应关系；HTTP注入不能代替真实网络和数据库测试。
- [ ] 合成数据库覆盖重复确认、并发版本变化、中途失败、提交后响应丢失和恢复重试；记录、操作与积分最终状态一致，不重复执行。
- [ ] 两账户、切换期间迟到回复、权限撤回和后台任务核对归属，实际数据库连接的RLS与应用校验分别验证。
- [ ] 双设备、断网、删除和冲突有结果；代码回退与数据恢复分别演练，附件不会因回退静默丢失。
- [ ] 关键浏览器旅程和必要真机覆盖输入、菜单、长内容、确认、撤销和同步，保留#110、#117等原问题。[Playwright](https://playwright.dev/docs/intro)可用于自动化，真实手机仍需实际证据。
- [ ] 目标地区完整请求、取消、工具时长、连接池、日志脱敏、费用和宿主恢复有明确结果；研究结论不能记为部署通过。

出现业务规则重复、组件直接跨表写入、跨账户资料混用、迟到或重试重复执行、关键回归退步、资料连续性不可证明或需未经批准的兼容层时，停止对应试点并留证。只回退本批代码和配置，不清用户库。不能为了框架选择好看而降低既有验收。
