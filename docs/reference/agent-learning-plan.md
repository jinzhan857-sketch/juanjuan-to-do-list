## 1．从卷卷自己的问题出发

产品定位以[产品说明](../product/README.md)为准：生活日程和待办的可靠记录是基础，AI帮助准确理解、整理、查询和修改事务是主要AI能力。规划、聊天和主动帮助建立在相关记录、授权偏好与实际反馈之上。宠物和积分继续提供陪伴与反馈。

借鉴是否有用，先看能否改善这些事情：随口表达少填表；日期、时间和多事项拆分更准确；修改不影响无关事务；取消、重试与换设备不弄丢内容；规划引用当前事实；提醒有用且不过量。框架名称、工具数量和演示热闹程度不作为采用理由。

记录含义要分清：计划记录的是打算做什么，完成反馈才说明用户报告做过什么；模型的归纳是可纠正的建议。不能仅凭“安排了很多学习”推断已经学会、状态不好或需要增加任务。

### 1.1．先把主要AI能力做扎实

复审结论：最直接适合卷卷的是结构化理解、业务校验、相关事实查询和结果验收。它们优先于常驻Agent和外部工具扩展，借鉴清单的编号不是施工顺序。

| 记录流程 | 卷卷需要做到什么 | 适合借鉴与自己维护的边界 |
| --- | --- | --- |
| 保存用户表达 | 原文、备注换行、附件及手动选择不因AI整理而丢失 | 沿用已有发布与#60成果；不让参考项目重写当前数据规则 |
| 理解与追问 | 区分日程和待办，拆分多事项，识别日期时间、修改意图与范围，信息不足时追问 | 模型处理语义，日期和业务合法性由程序检查；以已确认规则和#58、#59等专项为依据，不在借鉴方案里新定规则 |
| 展示与确认 | 用户可看清拟保存内容、目标和影响范围，手动字段优先 | 自己维护操作合同；Ajv等仅辅助结构校验，不能保证语义正确 |
| 执行与反馈 | 统一入口保存，核对实际结果，取消、重复请求和撤销保持正确 | 沿用卷卷身份、范围、快照、存储和计分规则；只补有证据的缺口，不复制第二套执行系统 |
| 比较效果 | 比较完整字段、整条任务和最终状态，记录用户修正负担及调用成本 | 优先复用现有合成用例和回归入口；另留未用作提示词示范的表达，不只比较回复是否流畅 |

最小对照先覆盖固定时钟下的明确日期、多事项、日程与待办混合、手改优先、信息不足、单次与整组、模型失败和取消。字段准确、最终写入与修改范围、修正次数、调用量和耗时分别记录，具体样本及阈值由#11和原专项确认；不预设必须接入某个框架才能改进。

权限、取消和重复执行保护贯穿整个流程。文章的原语不等于七个必须同时建设的服务；初期尽量在现有单后端和数据库内实现必要部分，具体方案须经审核和部署验证。

3.0先保住记录、账户同步、受控动作和原普通通知的完整流程。为这些流程保存确认与发送状态，不等于必须建立可自主持续工作的Agent平台；完整后台AI循环、自动目标跟进和外部事件订阅继续作为后续候选，不新增发布前置。

## 4．建议的最小边界

普通表单、完成反馈和确定性查询继续进入业务服务，由程序校验并读写事实。需要AI的表达先理解，形成结构化草案，再由同一个业务服务处理。规划和聊天按授权查询相关事实，提出建议；采用建议仍进入事务确认。

确有主动AI场景后的候选结构是：有效事件或到期任务，唤醒一次有上限的处理，读取当前事实与必要偏好，校验权限，执行允许动作或保存待确认状态，记录结果并按需触达，然后结束。普通到期提醒可直接由程序处理，不经过模型循环。后台AI任务可先按用户控制并发；普通表单保存不被慢模型阻塞。实际锁粒度和并发规则留给实现设计，不在本轮创建服务或表结构。

设计时至少区分以下职责，未要求为每项单独创建数据库或服务：

- 业务事实：日程、待办、用户完成反馈、积分宠物及已有操作记录，以真实编号和版本定位。
- 运行与确认：本次目的、会话、输入事件、动作草案、状态、取消、待确认与最终执行结果。
- 定时与触达：关联业务对象和本次发生，区分未到期、处理、发送、失败与已失效。
- 长期偏好与派生摘要：来源、时间、授权、确认或推断状态，纠错与删除能影响相关派生内容。

不复制第二套日程、积分和权限逻辑。在线业务继续优先JavaScript，Python优先作独立评测、分析和模型实验，详见[决策0003](../decisions/0003-javascript-python-boundary.md)。Anthropic文章不要求绑定某家模型或Python框架。

### 4.1．账户、授权与可恢复状态

读取资料、构建模型上下文、执行动作和记录日志都按当前账户与用途约束。模型返回一个存在的编号不证明该账户有权访问；切换账户或撤销授权后，原请求与后台结果不得回流到新账户。关闭个人记忆后，按关闭规则停止选取历史个人记忆，当前明确输入仍可正常处理；闲聊不因系统拥有日程就默认读取全部安排。

来源删除或授权收回后，相关摘要、缓存和检索结果须失效或按规则复核，不得经旧摘要或历史快照再次作为有效偏好注入。数据删除与审计保留范围由#13、#17、#18具体设计，不以“可恢复”为由永久保留原文。

事件编号去重不能单独保证业务只执行一次。方案应区分业务请求编号、确认版本、事务提交与积分结算保护；中断后查询实际执行结果，状态不明时停止或复核，不盲目重放。通知投递则另行处理，不把数据库中的去重等同操作系统只显示一次。

## 5．nanoMuse哪些继续学，哪些暂不学

| 处理 | 内容 | 原因与限制 |
| --- | --- | --- |
| 有缺口才研究小机制 | 授权绑定、单任务预算、上下文保留、记忆变更记录 | 主线仍是记录准确；先对照已有保护，不能因为参考项目有模块就再写一套确认、快照或撤销 |
| 先学流程，后验证 | 用户主动发起周复盘、会议准备、猫的执行状态 | 对生活场景有直接价值；更换数据入口和界面，不继承默认邮件、文件和脚本权限 |
| 仅独立评测参考 | 目标结果判定、重试恢复案例 | 适合检查系统最终状态，不证明用户现实目标达成；不用作自动奖惩依据 |
| 暂不接入整套实现 | Python运行时、单人SQLite数据层、多端客户端和设备中继 | 和当前Node.js、账户同步方向存在额外适配及维护成本，缺少整套接入的必要性 |
| 保留后期候选 | 外部日历、MCP、持续目标跟进 | 需要先有稳定事实与权限接口，以及明确场景、运行成本和验收 |
| 当前不学其宽泛执行范围 | 屏幕点击、任意应用操作、自动安装技能、多Agent分工 | 暂不能直接改善记录准确性，会增加误操作、权限和维护难度；远期也须有具体收益，不作为4.0默认目标 |

暂不采用某部分不等于否定整个项目。现有审查不足以评价其全仓代码质量，也不把朋友的整体评价当证据。所有直接复用均先核对具体提交、文件与许可；换语言不消除原许可要求。

## 9．最小试验与验收草案

下面是供对应任务选择与冻结的合成场景设计，均未执行，不计入现有测试通过数。具体日期和范围使用固定时钟，不读展的真实资料。

| 场景 | 需要核对的结果 |
| --- | --- |
| 一句话包含两项生活事务 | 按用户意思形成独立候选，信息不够则追问，保存数与确认数一致 |
| 只改重复日程中的某一天 | 只影响真实编号对应的那一条，整组与无关记录不变 |
| 模型返回无效或过期编号 | 拒绝写入并解释重新选择路径，不能模糊选中另一条 |
| 用户稍后确认，目标已被另一设备修改 | 保存的确认不能覆盖新事实，需要重新核对并确认 |
| 连点确认或网络重试 | 同一动作只产生一次业务结果与一次适用积分变化 |
| 用户取消后模型或工具迟到返回 | 不产生新写入，不覆盖新请求，也不继续提醒 |
| 提醒到期前日程被改期或删除 | 旧触发失效，新触发对应当前记录，不重复发送 |
| 后台执行中断后恢复 | 按持久状态确定继续、复查或停止，不能盲目重做已发生写入 |
| 已授权且按频率规则选中的普通提醒 | 程序可直接判定，AI调用数为0；实际触达与发送请求分开验证 |
| 规划遇到旧记忆与本次要求冲突 | 当前明确要求优先，建议能指向有效记录，不能自动改日程 |
| 用户拒绝整理记忆或删除来源 | 不应用被拒变更；派生摘要失效或要求重验，不从历史快照恢复成有效偏好；审计保留范围由原任务明确 |
| 周复盘与主动建议 | 引用相关记录，区分计划与实际反馈；无有用内容可不发，频率服从用户设置 |
| 模型超预算、超时或服务不可用 | 明确结束或重试路径，普通记录功能可用，错误不变成成功文案 |
| 开启免打扰或多设备接收 | 依规则抑制或延后，按同一发生编号处理；安卓与iPhone实机另验 |
| 日程和无日期待办混合输入 | 固定日期时间的事项与明确日期未定的事项分开，字段按已确认规则落地，不把所有事项强行同日保存 |
| 精确时间、模糊时段和跨年表达 | 按原规则核对完整日期、时间和必要追问，不由模型或本方案另造默认值 |
| 手选字段后再次AI识别 | 核对日期、时间、备注、标签等手选优先及原文附件保留，不把旧AI结果覆盖新手改 |
| AI追问后用户改口或排除某一天 | 以最新有效要求核对目标和影响条数，保留原始表达，不合并相互冲突的指令直接执行 |

| 业务提交后进程中断、事件再次处理 | 以业务请求及实际提交结果核对，事务、积分与宠物不重复变化，不能仅凭事件状态再次写入 |

## 10．停止与回退条件
