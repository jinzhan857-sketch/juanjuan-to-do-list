# 0003 JavaScript 在线业务与 Python 独立工具的分工

日期：2026 年 11 月 15 日。状态：展已授权记录以下原则；具体依赖、算法、Python在线服务与未来版本功能仍须按任务验证，不在本轮实施。

## 1．选择与原因

延续[决策0002](0002-backend-language.md)：卷卷前端及在线业务后端优先JavaScript。Python优先用于独立的评测、数据分析和模型实验，只有具体需求和效果证明必要时，才另行设计在线计算服务。

这补充语言分工，不推翻Node.js方向，不为可能用到的机器学习能力提前建设第二套后端，也不要求把nanoMuse整套Python代码翻译成JavaScript。

## 2．按职责选择

| 工作 | 默认选择 | 判断依据 |
| --- | --- | --- |
| 页面、账户、同步、权限、日程和待办、确认执行、积分与宠物、恢复 | JavaScript及数据库 | 关键业务规则只维护一份，复用现有语言与验证 |
| 大模型API、工具调用、周复盘、记忆整理、普通检索 | 优先JavaScript | 调用AI不等于训练模型，不能仅因此引入Python服务 |
| 完成率、分类、数量、时长汇总与常规趋势 | JavaScript或数据库查询 | 简单统计直接计算，先保持容易核对 |
| 批量模型评测、失败分类、回归报告 | 按工具适配选择，可独立Python | 若现有JavaScript评测工具更省维护就沿用；无需把评测放在线请求里 |
| 较复杂数据清洗、统计分析、聚类和预测实验 | 适合独立Python | [pandas](https://pandas.pydata.org/docs/)及[scikit-learn](https://scikit-learn.org/stable/)等有成熟工具，采用前仍需明确分析问题与数据质量 |
| 模型训练、微调、本地推理或专用科学计算 | 有明确需求时评估Python | 当前未确定要做这些能力，不因列出就成为3.0交付项 |

例如“本周完成多少任务”直接统计。“依据历史记录估计一类事务耗时”才可能值得建模；先与简单规则比较，证明数据和收益足够，再决定上线，不把模型数量当项目专业度。

## 3．优先把 Python 留在独立工具层

建议先采用这条路径：经授权的合成样本或必要只读数据输入，Python完成评测、分析或模型实验，输出JSON、报告或模型文件，再由开发者判断是否采用。个人原文不自动进入训练、公开样例或外部模型。

用户查看、创建和修改事务不依赖开发电脑运行Python。工具不开、实验失败或暂不采用，都不应阻断卷卷正常使用。需要何种实际数据、运行费用和模型调用，仍按对应任务授权，不由本次资料整理取得。

## 4．什么情况下才新增在线 Python 服务

仅当以下问题都有明确答案后，再提出具体方案供展确认：

1. 用户在产品内确实需要实时或后台计算，离线报告不能满足需求。
2. 已有Python实现或依赖有清楚价值，与现有JavaScript或数据库方案比较后，收益足以覆盖新增维护成本。
3. 数据与样例足够，结果在固定场景中通过验证，耗时、费用、出错及恢复可接受。
4. 部署、接口、认证、隐私、许可、版本和运维责任明确，具体托管环境能支撑任务时长。

若通过，JavaScript后端负责身份与资料选择，调用职责单一的Python计算服务，接收版本明确的结果或建议；用户确认、最终业务写入、积分和宠物结算仍由JavaScript业务层掌握。应明确超时、取消、重试和任务编号，避免一项任务执行两遍。

Python计算服务不复制另一套日程、同步、积分规则，也不拿管理员凭据直接改用户业务资料。长任务按持久任务设计，不让网页请求一直等待。不能在未获授权时顺手增加兼容或降级逻辑。
