# 发布、版本与恢复

本文区分已经核对的发布事实与后续要建立的流程。本轮没有部署网站，也没有把文档版本叫作新应用版本。

## 当前发布事实

配置文件 `.openai/hosting.json` 声明 Sites 静态目录为 `dist`。盘点时 `dist/index.html` 与根目录当前源码不同，没有自动构建或同步步骤。

Sites 最近核对的保存版本为第 8 版，来源应用提交 `b35936b…`，平台显示部署成功。命令行对首页和 API 的历史探测返回 403，未完成普通浏览器与真实 API 的完整验收。详情见[现状清单](../CURRENT_STATE.md)。

当前 GitHub 文档更新不会自动证明线上应用已更新；也不能凭 `.openai/hosting.json` 保证 Node 接口已经托管。不要向曾触发凭据弹窗的 `sites-publish` 远端填写密码或试推，后续发布通过已确认的平台能力处理。

## 正式发布前要建立的流程

1. 确定应用代码提交、版本号与发布范围，保证未提交成果有明确归属。
2. 用可重复命令生成发布目录，核对产物来源，消除手工复制漂移。
3. 执行相关规则、存储、界面与必要模型检查，归档结果。
4. 核对配置、前后端路由与目标地区可访问性，记录不含密钥的配置名称。
5. 涉及数据变化时先确认备份、迁移与恢复演练。
6. 在已授权范围内部署，完成线上冒烟检查，再记录版本标签、Release、平台版本与证据链接。

这是一份待落实的发布要求，不是当前已可一键执行的命令。版本命名需统一页面 V2.2 与历史设计中的 V2.0 基线增强说法，避免只改标题就宣布完成。

## 回退与停止条件

代码回退、平台回退和用户数据恢复分别验证。保留旧应用提交及产物记录，确认平台回到哪个版本；数据恢复使用独立备份与已演练步骤，不能用 `git reset` 当作数据库恢复。

出现数据覆盖风险、越范围修改、关键测试退步、配置无法复原或核心链路不可用时，停止本次发布，保留错误和测试证据。不在用户数据上临时清空或通过重新部署掩盖问题。

Git 标签、Release 和站点回退流程都需要后续任务实际验证，见[路线图](../ROADMAP.md)。
