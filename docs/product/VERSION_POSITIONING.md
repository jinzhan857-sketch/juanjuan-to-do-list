# 卷卷版本定位与开源借鉴：1.0 到 4.0

更新日期：2026年11月17日。本文统一说明产品阶段、版本边界与借鉴入口。V2.6与V2.7已正式发布，当前重要里程碑为V2.7；V2.8至V2.9承接渐进框架迁移，V3.0承接账户与多设备协同等完整体验。最新决定见[决策0006](../decisions/0006-version-milestones-and-isolated-rollout.md)。沿用本文件路径，不追溯修改旧版名称。

卷卷以生活日程和待办的可靠记录为基础，事务理解与整理是主要AI能力；规划、聊天和提醒建立在相关事实与授权资料上，定位以[产品说明](README.md)为准。后续运行架构主要参考Anthropic，nanoMuse保留局部参考。

[具体借鉴与学习方案](../reference/agent-learning-plan.md)逐项列出学什么、不学什么、理由、试验、候选版本和原任务映射，已按[PR复审](../audit/2026-11-15/pr75-review.md)收紧并合入。选中原则已细化到原任务，周复盘单列[3.x候选#78](https://github.com/jinzhan857-sketch/juanjuan-to-do-list/issues/78)，见[整合报告](../audit/2026-11-15/pr75-plan-integration.md)。具体库、阈值和未定功能仍待对应任务确认；当前修复顺序和原位置勾选保留。

1.x 和 2.0 按展提供的早期资料归纳产品演变，不逐个考证上线日期。1.4 左右作为早期过渡标志，比把仅调整文案的 1.5 写成重大升级更合适；提示词编号不等于每次都有对应的正式发布。当前实现看[状态页](../STATUS.md)，开发顺序只在[总计划](https://github.com/jinzhan857-sketch/juanjuan-to-do-list/issues/1)维护。

## 1．各个标志版本是什么

| 标志版本 | 定位 | 代表性变化 | 状态 |
| --- | --- | --- | --- |
| 1.0 | 能通过做事养猫的个人规划工具 | 以提前规划、完成反馈、积分、食物和喂养卷卷形成基本流程；已有日历、本地存储、备份和 AI 辅助价值评分 | 早期阶段回顾 |
| 1.4 左右 | 宠物与行动反馈规则逐渐成形 | 从性格标签改为精力与计划风格，区分饭量、饱线和成长反馈，并持续调整小猫表现与操作体验 | 本文选定的早期过渡标志，不新增历史发布 |
| 2.0 | 宠物陪伴式个人事务助手 | 区分有日期的日程与随手待办，引入聊天助手、重复日程、批量操作确认、规划建议和个人记忆等方向 | 历史定位；旧方案中的每项要求不等于当时均已完成 |
| 2.5 | 功能已较丰富，进入工程整理与可靠性补齐 | 保留日程、待办、助手、记忆、积分和宠物，整理源码、构建、测试、数据保护及发布流程，逐项修复日常使用问题 | 已发布的历史阶段，成果与任务原位置保留 |
| 2.6 | 自配AI可用与当前代快速稳定发布 | 自配真实聊天、搜索、网页与图片；确认写入、编辑删除与撤销、备份恢复、版本来源与发布核对 | 已正式发布，来源5ffbce4，详见#10；完整手机及复杂质量矩阵继续#55/#135 |
| 2.7 | 低门槛云端AI与首次体验的重要里程碑 | 无需Key的真实云端AI、确认式记忆导入、首次2日程3待办、设备累计卡、长输入回复、首页提醒及界面调整，统一自动理解 | 已正式发布，来源582aac4；实施#147、发布#148，云端主任务#82，业务资料仍在本地 |
| 2.8至2.9 | 渐进更换框架与工程边界 | #123先存档和方案，再借#124真实模块完成只读试点，随后逐流程迁入；独立网址并行试用 | 已确认方向，尚未实施；不自动替换V2.7正式入口 |
| 3.0 | 可以跨设备使用、操作受控的云端个人事务助手 | 独立业务后端、账户与同步恢复、桌面与手机界面、开发者配置与诊断、AI工具权限；保留宠物、记忆与通知承诺 | 已规划尚未交付；主动提醒与主动思考属本代方向，首发最小场景和完善批次由#11逐项冻结 |
| 3.5 左右 | 能持续跟进目标的主动型个人助手 | 在稳定账户和同步之上，试验经授权的目标检查、周期复盘、记忆整理、事件触发与少量外部只读连接 | 概念候选，尚未讨论清楚；实际里程碑也可命名为 3.4 或 3.6 |
| 4.0 | 更完整的生活规划与行动协助 | 可深化记录、规划与实际反馈的完整流程，按需要连接少量外部服务；跨应用和设备操作只保留为备选 | 概念候选，尚未讨论清楚，不以通用执行平台或操控设备作为升级条件 |

## 2．标志版本之间在做什么

| 区间 | 主要工作 | 阶段边界 |
| --- | --- | --- |
| 1.0 到 1.4 左右 | 把规划、积分与养猫的基本流程打磨顺，调整姿势、动画、标签、设置和使用反馈 | 还是以表单、日历和宠物反馈为主的本地工具 |
| 1.4 左右到 2.0 | 继续调整精力与成长规则、价值评分及说明，逐渐扩展到更完整的个人事务管理 | 1.5 文案、1.6 价值评分、1.7 预估显示等是过程记录，不逐个包装成大升级 |
| 2.0 到 2.5 | 扩展日程、待办、聊天、记忆、附件、确认和撤销等能力，随后补齐工程组织与验证 | 能力较多，但仍主要是浏览器本地应用 |
| 2.5至2.7 | 修稳当前代，交付自配AI与云端AI，补首次体验、记忆导入和额度卡 | V2.6、V2.7实际发布分别留证，原任务先后与完成位置不改变 |
| 2.8至2.9 | 渐进更换框架，拆分真实业务边界，独立试用并逐流程验证 | V2.7稳定站继续保留，新框架先用另一网址一段时间；切换需功能、资料、恢复、真机、来源、回退和该次授权 |
| 3.0 | 账户、多设备协同、桌面界面和开发者模式形成完整体验，明确受控主动能力首发范围 | #11冻结首发与完善清单，#20负责实机验收发布；页面适配不自动等于安装式桌面客户端 |
| 3.0 到 3.5 左右 | 用 3.1、3.2、3.3 等持续查错与增强；先用户主动发起复盘，再按验证结果试验主动跟进 | 3.x 增强建议尚未冻结到每个小版本，不自动把 3.0 原任务后移 |
| 3.5 左右到 4.0 | 先验证持续帮助的价值，再选择深化生活规划、行动反馈或有限外部连接 | 以实际需求、成本和成功证据选择方向，外部执行不是必经阶段，不为编号建设通用平台 |

V2.6与V2.7已成为实际发布记录，不再作为未来候选批次。V2.8至V2.9是展确认的框架迁移建设区间，具体批次仍按#123验收，不为凑编号发布。3.1、3.2、3.3属于3.0这一代的小步测试与增强；3.5仍只是可选阶段标志。

## 3．怎样判断该换版本

1. 小版本对应一批有共同目标、能说明结果的改动。单个 Bug 每修一次、手机每测一轮，不必都换产品版本号。
2. 同一版本可写“测试第 1 轮”“测试第 2 轮”，另记源码提交和构建来源；产品版本、测试轮次、文档草稿版分别管理。
3. 大版本对应用户能力或完整使用流程的明显改善。2.x 到 3.0 以账户、同步和受控 AI 业务流程为主要变化；4.0 的边界待专门讨论，不以外部工具或设备数量决定。
4. 开始建设可写“3.0 开发中”。只有冻结的首发范围通过验收并实际发布，才记作“3.0 已发布”。文档、分支或 main 合入均不能替代发布。
5. 版本数字不是小数，不以补齐所有中间数字为目标。1.4、1.6、3.5 等阶段名可以按实际内容选择，历史名称不追溯改写。

当前正式页面为V2.7，业务备份格式仍2.2，产品版本与数据格式分开。本文整理不改页面、接口、依赖或部署；发布事实分别进入#10、#82及#148。

## 4．3.0 首发和 3.x 增强怎样分清

现有[3.0 共识稿](../V3_CONSENSUS_DRAFT.md)、[决策记录](../decisions/README.md)和 #11 至 #20、#34、#41 继续有效。本次不删除任务、不降低验收、不把未完成事项标成已完成，也不直接重排它们。

3.0 首发重点核对以下完整流程，具体场景与门槛仍在 #11 冻结：

- 本地试用、邮箱账户、登录连续性、账户数据隔离与跨设备同步能按确认规则工作。
- 日程与待办的新建、修改、确认、取消、重复请求、撤销及积分与宠物结算可核对；旧数据保留与恢复能验证。
- AI 的实际请求、失败、取消、费用与额度能追查；工具和数据变更不能绕过程序校验。
- 桌面端界面与开发者模式分别承接#34和#17，开发者能够核对配置、请求和错误；具体开放范围在#11确认。
- 已确认的布局、猫美术、记忆试验和普通通知仍由原任务按范围验收；真实电脑、安卓与 iPhone 的必要流程分别记录。

主动提醒、卷卷主动思考是展明确的V3.0这一代方向，#11需区分首发最小场景和之后增强，不能仅凭本文整体推迟。更强的自动记忆、主动晨报、持续目标跟进和外部工具逐项验证，不把普通通知当成这些均已交付。若要改变已确认的3.0范围，须在#11列明具体变化并由展确认。

## 5．版本与借鉴采用边界

| 阶段 | 值得研究的能力 | 本次安排 |
| --- | --- | --- |
| 当前 2.x | 用已有保护和测试修稳记录、查询和修改流程 | 不插入架构或开源接入任务，不改当前修复顺序 |
| 3.0 | 记录AI的理解、校验、确认和保存，账户同步、受控动作及原普通通知 | Anthropic作为必要运行机制参考，nanoMuse提供局部对照；不把完整常驻Agent、事件总线或所有原语设为必做项 |
| 3.x 小步增强 | 主动发起的周复盘、经确认的记忆整理、少量主动建议 | 周复盘已登记为#78候选，其他增强按原任务核对；先小试再决定扩大，小版本号待实施时确定 |
| 3.5 左右候选 | 持续目标检查、事件触发、周期例程、外部日历只读接入、有限的外部工具 | 只保存方向，需明确常驻运行、权限、打扰频率和维护成本 |
| 4.0 候选 | 更完整生活规划、行动反馈与必要的外部连接；跨应用和屏幕操作仅为备选 | 暂未形成完整范围，先证明用户收益，不作为3.0前置，也不预设卷卷必然变成通用执行助手 |

原本已确认的普通网页通知与数据库健康检查仍在 #19，不因“主动型助手”被放到后期而全部推迟。详细取舍与任务维护方式见[借鉴方案](../reference/agent-learning-plan.md)，nanoMuse源码与局限见[局部研究](../reference/nanomuse-research.md)，语言分工见[决策0003](../decisions/0003-javascript-python-boundary.md)。

Anthropic文章是架构方法参考；具体SDK与组件按收益选择；Grok Bot和Meta Muse作为产品体验参考，不能视为开源代码供给。参考层级与采用结论以借鉴方案为主要位置维护，不把全套参考内容变为版本必做清单。
