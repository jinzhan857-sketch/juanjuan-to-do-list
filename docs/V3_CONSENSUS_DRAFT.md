# 卷卷 3.0 共识与范围草案

版本：D0.1。日期：2026 年 11 月 14 日。状态：完整版核对稿，待展审阅。

本稿汇总当前代盘点、原飞书方案与本轮讨论，供产品、开发与后续接手者共同核对。它记录目标和范围，不表示 3.0 已实现，也不代表其中每项技术选择都已通过验证。确认后，再拆成 GitHub 总路线图与可执行子任务。

GitHub 与飞书均保存本稿全文，章节、表格和版本标识保持一致。GitHub 保存版本与后续实施记录，飞书作为完整阅读和讨论入口。修改先形成新版本，再同步全文；两边都不独立维护另一套结论。

## 1．目标、用户与成功标准

卷卷 3.0 的第一优先级，是形成一个能够展示产品判断和技术能力、实际可用、可解释、可配置、可验证并可持续接手的完整个人事务 Agent 项目。它同时服务展的日常使用，并允许朋友与面试官低门槛试用。

卷卷以宠物陪伴为特色，帮助用户将零散表达整理成日程与待办，根据实际安排和授权资料提供规划建议，并支持不同设备继续使用。展能够调整关键行为配置，知道错误发生在哪里，通过测试比较改进效果并恢复旧版本。

首批长期用户是展本人，主要在香港使用。外部试用者主要在中国大陆。展示需要真实可运行的用户流程、清楚的设计理由和验证证据，不能只展示后台页面或架构名词。

完成应同时体现三类结果：用户可以完成核心事务；系统能保护数据、定位失败与验证改动；GitHub 资料足以让其他人或 Agent 理解并继续迭代。具体的首批场景、通过标准、耗时及费用门槛，后续单独讨论后冻结。

## 3．现有基线与保护范围

当前代以单文件网页为主，已有日程、待办、聊天、个人记忆、宠物、积分、备份与部分 AI 接口。首次盘点已核对本地源码、GitHub 提交和 Sites 发布记录，并记录本地尚未发布的改动。完整事实见仓库内 docs/CURRENT_STATE.md，不能把 3.0 设计描述当作当前能力。

现有宠物、积分及已确认的核心能力继续保留。若个别规则存在具体问题，应单独定位、讨论和验证，不在重构时顺带删减。规则评分的预设数值、编辑权限与 AI 评分的一致性，后续需形成专门规则表。

已知优先问题包括：单天请求可能被误识别为整组修改；托管上下文丢失组身份；旧记忆城市可能压过当前明确地点；源码与发布产物不同步；导入和批量执行缺少整体失败保护。这些应成为后续修复任务及回归案例，不用目录重排掩盖行为错误。

原始资料、代码改动、旧数据及历史失败记录应保留。旧版本升级后，用户仍应看得到并正确使用原有日程、待办、宠物、积分和记忆。

## 4．用户入口、事务发布与评分

统一使用“事务”作为上位概念，事务分为“日程”和“待办”。日程有执行日期及相应时间信息，待办用于无固定执行时间的事项。既有细分规则需在后续数据合同中明确。

发布表单底部并排两个按钮，左侧为“AI 评分”，右侧为“快速发布”。两者不是两套独立业务模型，最终进入相同的校验、保存、积分和宠物规则。

| 入口 | 是否调用 AI | 预期行为 |
| --- | --- | --- |
| AI 评分 | 是，作为默认辅助路径 | 识别与整理事务属性、生成基础价值判断；用户核对并完成发布 |
| 快速发布 | 否 | 根据用户填写的必要信息与预设方案给出规则分，并完成发布；信息不足时提示补充 |
| 卷卷聊天框 | 是 | 事务、规划、聊天三种模式均通过 AI API 理解自然语言 |
| 普通界面操作 | 按功能需要 | 查看、填写、编辑、完成等操作不应被无关的模型调用阻塞 |

规则评分可以采用保守预设，但具体分值不能在本稿中凭空确定。应说明评分依据，避免把 AI 返回值直接当成不可核对的最终结算。最终积分由程序按规则计算。

AI 不可用时，聊天框明确说明错误并提供重试或返回表单的路径，不用固定套话假装模型已经理解。快速发布继续可用；免登录或登录失效并不意味着 AI 可以离线运行。

普通表单的发布按钮本身可以构成用户确认；模型建议产生的真实数据变更应先展示明确的待执行内容。确认强度与影响范围匹配，不要求所有低风险操作重复弹窗。

## 5．一个卷卷与三种处理模式

普通用户面对同一个卷卷与聊天入口。三种模式用于划分职责与能力，不要求建设三套相互独立、反复交接的自主 Agent。角色可以共享模型接入、工具和数据访问模块，用户也保留手动选择的入口。

| 模式 | 主要职责 | 写入边界 |
| --- | --- | --- |
| 卷卷事务 | 理解日程与待办的查询、新建、修改、删除及重复组需求 | 输出清楚的操作草案，校验与确认后由程序执行 |
| 卷卷规划 | 基于近期安排、待办、授权记忆和系统计算事实提出建议 | 规划建议需要落地时交给事务流程重新校验与确认 |
| 卷卷聊天 | 普通交流、答疑及适合的实时工具需求 | 不在聊天回复中声称已完成未执行的数据变更 |

模型理解意图与语义，程序确认目标身份、日期计算、重复组、冲突、合法性和执行结果。自然语言不能全部依赖不断加长的关键词规则，模型结果也不能绕过程序校验。

简单请求尽量减少不必要的模型轮次；只有复杂任务才增加必要步骤。所有模式保留明确的取消、失败和结束条件，不依赖无限循环。

## 6．系统分层与后端责任

| 层次 | 负责内容 | 边界 |
| --- | --- | --- |
| 用户界面 | 桌面和手机网页、日历、表单、聊天、记忆、宠物和状态提示 | 不把服务端密钥、权限判断和全部业务规则交给页面 |
| 业务服务 | 身份、数据访问、评分结算、日程组、冲突、确认、执行、撤销、同步 | 由程序保障关键规则，按职责分模块，先使用一个清楚的后端项目 |
| AI 运行 | 角色处理、上下文选择、模型调用、工具调用及结果校验 | 模型输出是候选理解与建议，不直接成为数据库命令 |
| 配置与治理 | 提示词、工具权限、工作流、案例、测试、运行记录、版本发布 | 草稿与正式版本分开，配置不能关闭底层保护 |
| 数据与调度 | Supabase、备份、迁移、通知任务、健康检查 | 运行数据独立于代码部署；定时任务不依赖个人电脑开机 |

推荐以 Python FastAPI 实现确定性业务和接口，先验证 Vercel 托管组合。选择依据是接口清楚、便于测试与托管，不以“使用 Python”本身证明稳定。需检查香港与大陆访问、数据库连接、模型流式输出、任务持续时间、免费额度及未来商业使用条件。

用户确认可能发生在数分钟之后，待确认操作与执行状态必须持久保存，不能让一个网络请求或内存对象一直等待。部署环境变化和请求重试不能导致重复创建或遗漏结果。

后端托管平台仍属推荐待验证项。验证失败时先调整部署方案，不因此推翻业务规则和数据合同。

## 7．提示词、上下文、工具与工作流配置

| 模块 | 内容 | 管理方式 |
| --- | --- | --- |
| 产品及角色指令 | 职责、表达、判断原则、禁止编造 | 独立配置，可比较版本 |
| 上下文选择 | 本次可读取的日期范围、数据量、相关记忆与历史 | 程序选择资料，配置允许的范围 |
| 输出合同 | 回复类型、动作、字段、必填信息 | 模型获得格式说明，程序执行结构与语义校验 |
| 工具定义 | 用途、输入输出、所属角色、读写性质、失败表现 | 可配置已开发工具的启用与组合 |
| 工作流 | 开始、步骤、条件、追问、交接、失败出口、结束 | 首版推荐固定节点与表单式编辑 |
| 界面文案 | 处理状态、错误、确认与结果说明 | 与模型指令分开维护 |

“分层”不意味着每层都调用一次模型。可配置内容也不等于任意代码可编辑。新增真实工具、数据库变更、新节点能力与权限机制，仍属于开发任务。

工作流首版可调整角色提示词、上下文范围、允许的工具、条件分支、追问、交接、读取重试与超时。账户权限、写入校验、必要确认、重复执行保护和操作记录由程序强制保证。

示例流程：理解重复课程需求，追问关键缺口，展开日期，检查重复与冲突，展示确认卡，用户确认，程序执行，记录结果并按条件允许撤销。

复杂拖拽画布和任意脚本节点暂不作为首版目标。完整节点清单、允许连接关系、循环上限和预览方式仍需设计与测试。

## 8．开发者控制台、评估与运行记录

展希望提示词、角色规则、案例、工作流和工具组合方便调整，即便实际主要由 Agent 操作，也要知道修改入口与影响范围。模块化管理和调试能力属于 3.0 核心范围，不能仅做展示页面。

首版控制台应能查看和调整关键配置、保存草稿、比较差异、运行选定案例、查看测试结果、发布配置并恢复上一稳定版本。配置变更应绑定修改原因、依赖与验证结果。

运行记录至少关联请求标识、角色、配置版本、读取资料类型或来源、流程步骤、模型与工具耗时、校验结果、确认与执行状态、错误类型。记录用于解释处理过程，不要求展示模型隐藏推理。日志保留期限和敏感内容范围需要单独设计。

示范案例、验收案例和历史失败案例分开。验收答案不直接作为每次回答的示范输入，真实用户资料不自动进入公共案例库。失败修复后沉淀成长期回归案例。

## 9．数据存储、账户与登录连续性

| 位置 | 保存内容 |
| --- | --- |
| GitHub | 代码、设计文档、测试、数据库结构和迁移脚本、适合保存的验证证据 |
| Supabase 云端 | 账户数据、用户业务数据、配置及受控运行记录，具体表结构后续设计 |
| 当前设备 | 免登录试用数据、缓存和未同步修改 |
| 独立备份位置 | 可恢复的数据导出与必要附件，不保存进公共代码仓库 |

数据归属以账户身份为边界，所有登录用户只访问自身授权的数据。管理员可以管理产品配置，不因此默认拥有任意查看用户私人资料的权限。

首版采用邮箱验证与密码登录，后续再增加短信和微信。默认保存会话并自动刷新凭证，避免设置不必要的短登录周期。主动退出、修改密码、清理浏览器等情况下仍可能需要重新登录，不承诺永久登录。

网络断开或凭证暂时失效时，保留可用的本地数据和未同步修改，不阻塞本地操作。同步前优先自动恢复认证，确需用户操作时再提示登录。主动退出与共享设备的数据清理需提供明确选择。

首次登录应预览试用数据是否并入账户，避免静默覆盖。账户切换时隔离本地缓存，不能将上一账户资料上传给另一账户。具体合并与共享设备交互属于待设计项。

## 10．跨设备同步、旧数据迁移与备份

登录后的电脑与手机访问同一账户数据。第一版支持按钮同步，显示已同步、未同步修改、失败与最后同步时间。无需承诺即时更新，但不能无提示地丢失修改。

同步应处理记录身份、版本、删除状态、重复请求和冲突。两台设备修改同一记录时，保留冲突并提供可解释的处理，不以整份文件覆盖另一端。具体冲突策略和界面后续确认。

升级程序与保存用户数据分开。结构变化使用版本化迁移，先在数据副本上测试，迁移前备份，迁移后核对日程、待办、宠物、积分、记忆、附件和重复组关系。失败时保留原始数据与恢复路径。

当前浏览器旧数据迁入云端，必须先预览数量和归属，用户确认后上传，成功后核对。重复导入、中断后继续、错误格式与恢复均需测试。当前代已经存在的个人备份不能直接替代完整迁移验收。

定期导出、独立备份和恢复演练属于必要能力。选择 Supabase 不代表不可迁移：业务数据可导往其他 PostgreSQL 环境；账户、附件、权限和调度需要分别处理，不能承诺无成本换库。

## 11．个人记忆、持续整理与 RAG

日程、待办、积分与重复组是结构化事实，优先直接查询数据库与程序计算。用户确认的偏好和资料作为可查看、可修改、可停用、可删除的个人记忆，不跨用户，不进入公共知识库。

LLM Wiki 式持续整理纳入范围受控试验，目标是积累长期目标、偏好变化与资料关系，减少重复解释，不是先建设完整知识库平台。原始资料、确认事实与模型归纳分开，归纳关联来源和更新时间。

重要变化或敏感归纳先向用户提示确认，不能把模型猜测当成既定事实。来源修改或删除时，相关摘要需更新或失效；用户当前明确表达优先于旧归纳。整理按需触发，设置范围、频率与费用边界，不在每次聊天后重写所有资料。

试验应验证来源引用、偏好更新、重复询问减少和错误记忆控制。只有效果可验证才扩大范围；未验证前不以“具有长期理解”作为既有成果。

RAG 用于从课程大纲、文件、文章或长记录中检索回答依据，不等于一开始必须建设向量数据库。资料规模不是唯一条件，跨资料查证和原文依据需求也可以触发评估。首版具体文件问答场景尚未确认，不作为所有事务的前置步骤。

持续整理和检索可以结合：先利用已有主题摘要，再检索原文核实。资料访问权限始终先于检索，个人资料与公共帮助内容分别管理。

## 12．AI 接入、体验额度与费用

模型接入与业务规则分开，DeepSeek 与 MiMo 为已讨论的候选供应商。具体默认模型、版本与参数需经同一套场景评估后确定，并可配置调整。价格随供应商变化，不将本轮报价固定为长期成本承诺。

| 项目 | 初始共识或建议 |
| --- | --- |
| 访客设备或浏览器实例 | 每天最多 10 次公共 AI 调用 |
| 已登录账户跨设备合计 | 每天最多 20 次公共 AI 调用 |
| 全站公共模型调用 | 每天最多 50 次，当前是次数上限，不等同于金额上限 |
| 登录后是否同时保留单设备 10 次 | 建议保留，形成设备与账户双上限；精确叠加口径待核对 |
| 自带 API Key | 不占公共体验额度，密钥保存方式与代理路径需设计 |
| 快速发布 | 不调用 AI，不消耗 AI 额度 |
| 计数与重置 | 服务端核算；建议按北京时间每日重置，最终规则待确认 |

设备标识不要求严格识别自然人；不同浏览器或安装实例可能被识别为不同设备，不引入不必要的硬件指纹。公共额度由服务端控制，公共 Key 不进入前端代码。

次数、模型、单次输入输出上限、重试策略及账户等级均应配置化并保留变更记录，便于日后收拢额度或加入会员。当前不开发支付和完整会员体系。

一条用户消息可能触发多次模型请求。实际调用、失败、重试、扣减和退款口径必须写清，并展示剩余额度。单次用量和自动重试仍需上限；不能把全站 50 次当成固定金额保证。

用户自带 Key 不能写入日志、代码仓库或普通数据导出。是否仅当前设备保存、会话使用或服务端加密保存，属于待设计项，不沿用现有 localStorage 实现就宣称安全完成。

## 13．普通通知与数据库健康检查

网页通知作为 3.0 验证能力，默认关闭，用户主动开启并授权后使用，目标是一天 0 至 2 次普通通知。通知对象、时间、免打扰、跨设备重复和频率统计口径后续设计。暂不做闹钟式、断网必达或强提醒承诺。

桌面、安卓与 iPhone 都需实机验证。iPhone 网页推送需要考虑添加到主屏幕和系统通知授权。推送涉及浏览器、系统、网络与服务端，不以一次调用成功代替实际到达验证。

数据库健康检查每周两次，建议周二、周五，具体时间可配置。独立定时执行少量只读查询，保存执行结果，不调用 AI，不修改业务数据，也不依赖展的笔记本开机。

Supabase 免费项目按一段时间的低数据库活跃度判断是否暂停，并非保证七天内一次查询就不会暂停。健康检查降低风险，不能承诺永不暂停。仍需关注平台状态、保留恢复说明和独立备份。当前只确定建设方向，尚未创建定时任务。

每周健康检查不能替代通知调度。通知需要独立设计频率与到达验证；调度免费额度、失败重试和任务状态应在部署验证时一起检查。

## 14．测试、验收与发布保护

自动化为日常验证主体，PowerShell 等只是执行入口。已有页面自测与人工记录可以作为素材，但语法通过、函数存在或历史声明不能代替业务行为验收。

| 层次 | 主要检查 |
| --- | --- |
| 规则测试 | 日期时间、积分、重复组、冲突、目标定位与边界 |
| 接口与数据库测试 | 身份隔离、数据写入、重复请求、中断、迁移与恢复 |
| AI 场景评估 | 语义理解、结构输出、工具选择、真实依据、失败表现与费用 |
| 自动浏览器测试 | 关键页面、发布、确认、取消、错误与后端衔接 |
| 真实设备验收 | 手机键盘、布局、通知、登录与跨设备完整旅程 |

快速测试使用隔离数据，关键 AI 评估保留真实模型调用，不能只用模拟回复。记录模型与配置版本、数据集、执行命令、结果、失败案例、耗时和费用。验收检查最终数据状态，不仅检查回复是否声称成功。

首批验收场景与阈值尚待展进一步讨论。本稿仅建议覆盖：两种发布路径、混合事务、单条与整组边界、确认取消与撤销、规划依据、记忆纠错、长期登录、跨设备冲突、旧数据迁移、通知、模型异常及额度限制。它们是候选场景，不是已冻结的最终清单。

每批改动执行相关正常与异常检查，发布前跑关键回归。真实端到端验收放在阶段交付，但关键界面改动仍需适量浏览器检查，不能所有问题都留到最后。

## 15．GitHub、飞书与交付组织

仓库按展授权改为私有，开发阶段不全公开；网站试用范围另行管理。私有仓库不等于私人数据可以随意提交。未来公开展示范围、演示账号和资料脱敏需要单独核对。

GitHub 与飞书均保留完整版。GitHub 正式文档作为实施依据，飞书保持相同正文与版本，并保留阅读讨论用途。实际进度以 Issue 和交付记录为准，避免在两份正文中各自维护状态。

参考项目的做法是：README 提供入口，设计文档解释系统，总 Issue 按依赖串起任务，子 Issue 写目标、范围、前置、验收与交付链接，PR 关联代码与验证。卷卷借鉴这个组织方式，简化多人课程项目特有的手续，不把参考项目视为唯一标准。

建议保持一个长期主分支，任务分支按具体工作建立。正式版本对应可验证提交、测试结果和发布说明。当前不会为了外观先建立大量长期分支或无内容的 Issue。

本核对稿在仓库中标记为草案，不等于全部决策冻结。展核对后再整理 README 导航、总路线图与细粒度任务；未定内容使用设计或验证任务承接，不伪装为已完成事项。

## 16．推荐推进顺序与暂不扩大范围

| 阶段 | 交付重点 | 进入下一阶段的条件 |
| --- | --- | --- |
| 共识与当前代整理 | 核对本稿、基线、文档导航与任务组织 | 目标、范围与未定项可追踪 |
| 合同与最小后端 | 数据对象、动作协议、独立后端、环境验证 | 一条完整事务链路可运行并有隔离测试 |
| 用户数据与跨端 | 访客、账户、本地队列、同步、迁移与备份 | 旧数据保护与跨账户隔离通过验证 |
| 角色与管理能力 | 模型接入、角色、工具、配置、案例、追踪与版本 | 关键行为可调整、可定位、可验证、可回退 |
| 体验与记忆试验 | 规划、持续整理、普通通知、桌面和手机体验 | 具体收益与设备表现有证据 |
| 完整验收与交接 | 场景验收、发布恢复、演示和接手材料 | 发布阻塞问题解决，文档与运行状态一致 |

阶段内部依赖需要在任务拆分时细化，可以在满足前置后交错推进。暂不机械沿用旧方案的所有 V2.5 小版本号，也不在没有验收依据时直接宣布 3.0。

暂不扩大为：复杂多 Agent 网络、任意代码工作流、完整公共知识库平台、支付会员系统、大量第三方接入，或同时建设小程序与原生 App。额外客户端保留二选一方向，先用网页推送与移动体验结果判断必要性和交付阶段。
